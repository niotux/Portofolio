Assessment and scope

The eight original reproduced defects have local fixes and regression coverage. The fresh review also repaired reviewer accounting/JSON parsing, additional ineffective Git timeouts, and unread-output loss at small poll budgets. This is a reviewable local implementation; it has not been deployed or published.

This is a repository-wide, risk-based re-audit of the implementation after remediation, performed by the same local coding agent. It combines a refreshed source inventory, changed-code review, renewed inspection of all module families, targeted failure reproductions, the complete local test suite, solution build, CLI smoke checks and storage measurements. It is not an independent external review or a claim that every source line was formally verified. Deep inspection concentrated on cross-module contracts, execution, cancellation, transport identity, persistence, verification and restore; optional sidecars received lighter source review and compilation.

Baseline: f20e634b5101288fcbe787590cfbddf1c27d1ddc. Inventory: 384 source/config/script files; 78,429 lines. Source fingerprint: 57c32da51efde25468275052717d1b52d984420677a5c7cef3e21d5a1dae001d. The hashed inventory identifies the reviewed source snapshot independently of later documentation commits.

No factory team messages, KB publication, pushes, fleet settings changes, service activation or live model calls were part of this work. Tests and benchmarks used temporary local fixtures. No deployment canary is represented as completed.

Additional changes

  • Owned helpers. TaskTool is asynchronously disposed by the host. Helpers are bounded by seat lifetime, task scope and a 30-minute lifetime. At most 32 completed records are retained. Scope changes cancel older work; close reports unfinished cleanup honestly.
  • Usage attribution. Parent, helper and reviewer output are charged through a task-to-epic ledger. Helper completion keeps its original scope. Reviewer requests record category and parent task in telemetry. Ledger updates serialize concurrent budget charges; the ledger retains 128 scopes.
  • Shared process execution. Finite Git, review, provenance, live-facts, code-intelligence and update-startup commands use concurrent bounded stdout/stderr drains and tree cleanup. Shell/PTY, verifier process-group commands, binary desktop captures and long-lived MCP/LSP transports keep their specialized runners.
  • Operator settings. /settings shows allowlisted running values, installed tools, active telemetry, source hints, activation timing and cached factory switches without exposing credentials or making a fresh network call. A scalar merge-parity regression protects handwritten configuration wiring.
  • Bounded outbox reads. NotebookSync requests Pending(100); Take now precedes DeepClone. This bounds batch cloning while retaining causal order and acknowledgement semantics. Journal replay and acknowledged-operation scanning remain proportional to retained history.
  • Measured storage. PiSharp.RuntimeBench adds a reproducible local benchmark over disposable notebooks, including reopen, lexical search and pending-batch allocation. No database replacement or threshold change was justified by a synthetic benchmark alone.
  • Boundary handling. Malformed acceptance metadata becomes an unavailable manifest rather than crashing epic-budget discovery. The settings view applies the same nonpositive timeout/job-count fallbacks as execution.
  • Reviewer correctness. Rubric review usage/turn counts are recorded once per finished request. JSON parsing now respects braces inside quoted reasons. Bounded Git diff reads replace the separate unbounded runner.

What the code does and how it works

CLI/configuration → session and tool catalog → model transport → streaming agent loop → validation/guards → ordered tools → results and persistence → explicit continuation/verification → optional factory delivery. Session compaction and notebook recall shape the next request; checkpoints protect local worktree recovery. Factory integration is optional composition around the same core runtime.

Compatibility and operation

  • Turn hooks: DecideTurn takes precedence over ShouldStopAfterTurn. Stop ends, Continue requests the next model turn, and Poll keeps the established queue-polling behavior. Legacy callbacks still work.
  • Verification records: historical records without checkIdentity remain readable but are no longer eligible for reuse; checks run again. Unavailable workspace hashes never mean equality.
  • Checkpoint namespace: Windows retains case folding; Linux uses case-sensitive path identity. Existing lowercase-hash directories are preserved. A checkout whose new identity differs starts a new store. No ambiguous legacy data is automatically imported or deleted. An existing store bound to another worktree is refused rather than rewritten.
  • Acceptance manifests: prefer attrs.acceptance_criteria as [{"id":"tests","text":"tests pass"}]. A refusal returns the canonical manifest and its revision. Submit that revision as criteria_revision with ID rows. Explicit Acceptance / Acceptance criteria / Done when prose sections remain a compatibility source; exact canonical text rows remain supported. Unknown, omitted, duplicate or failed rows are refused. The local-only revision argument is stripped when the backend schema does not accept it. The existing feature switch and older-hub criteria capability check remain in force.
  • Interactive output: max_output_tokens now returns successive chunks from write_stdin; more_output=true means unread retained output remains. Call again with empty chars to drain it, including after process exit. A 256K-character retention buffer reports overflow. Status snapshots are observations and do not consume the cursor. Ordinary bash one-shot output caps still deliberately truncate their displayed result.
  • Settings: /settings reports selected operational values from the running state. Source labels are hints (project/global/default or runtime override), not a complete provenance ledger. Startup-installed tools require restart to change. Cached factory switch values can be stale until the usual refresh.
  • Cancellation: bounded cleanup returns control; it cannot force arbitrary managed code to stop. The context retains late task ownership and blocks new mutations until completion. Reads remain possible. External edits by another process are outside this ownership mechanism.
